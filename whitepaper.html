Abstract

NienCoin (NEC) is an independent Layer-1 blockchain designed as a peer-to-peer digital currency network. The network uses Proof-of-Work as its consensus mechanism and allows participants to operate nodes, verify transactions, and participate in block production.

NienCoin is designed around a simple monetary model: a maximum supply of 20,000,000 NEC, with new NEC entering circulation through valid block production according to the network's consensus rules.

The smallest denomination of the currency is called Huu Khang. One NEC is divided into 100,000,000 Huu Khang.

The project aims to provide a blockchain whose fundamental rules can be inspected, implemented, and independently verified by participants.

Design principle: The blockchain should be verifiable by its participants rather than relying on a single trusted operator.

1. Introduction

Digital currencies require a reliable method for recording ownership and transferring value without depending entirely on a centralized database.

A blockchain approaches this problem by maintaining a shared sequence of blocks. Participants maintain copies of the network's state and independently validate new information according to common rules.

NienCoin applies this general model to an independent blockchain network whose native currency is NEC.

The network is intended to allow a participant to install and operate node software, communicate with other nodes, receive transactions, validate blocks, and participate in mining.

The objective is not to make participants trust a particular server. Instead, the software rules should determine whether blocks and transactions are valid.

1.1 Problem Statement

A centralized digital currency can maintain a single authoritative database, but users must trust the operator of that database.

An independent blockchain attempts to distribute responsibility for maintaining the ledger among multiple participants.

The challenge is to establish a common transaction history when participants may not trust one another.

1.2 Proposed Approach

NienCoin uses Proof-of-Work to make block production computationally costly while keeping verification comparatively inexpensive.

Transactions are propagated through a peer-to-peer network. Miners construct candidate blocks and attempt to satisfy the current Proof-of-Work target.

Nodes verify received blocks before accepting them as part of their local view of the blockchain.

2. Vision and Design Goals

NienCoin is guided by several design goals.

2.1 Independent Blockchain

NienCoin is intended to operate as its own Layer-1 blockchain rather than as a token dependent on another chain.

2.2 Verifiable Rules

Consensus rules should be explicit enough that independent node implementations can determine whether a block is valid.

2.3 Mining-Based Issuance

New NEC is intended to enter circulation through block rewards generated according to consensus rules.

2.4 Peer-to-Peer Participation

The network should not require every participant to communicate with one central server.

2.5 Limited Supply

The maximum monetary supply is defined as 20,000,000 NEC.

2.6 Simplicity

The core protocol should avoid unnecessary complexity where a simpler mechanism can provide the required functionality.

3. The NienCoin Network

The NienCoin network consists of independent participants running compatible software.

Participants may perform different roles. A node may validate blockchain data. A wallet may create and sign transactions. A miner may construct blocks and perform Proof-of-Work.

These roles do not necessarily need to belong to separate machines.

3.1 Network Participants

  • Full nodes
  • Mining nodes
  • Wallet users
  • Network peers
  • Developers

3.2 Network Data

The principal types of data exchanged by participants include transactions, blocks, and peer-discovery or network-control information.

4. Blockchain Architecture

The blockchain is an ordered sequence of blocks. Each block is associated with the block preceding it, forming a linked history.

A simplified representation is:

Each block contains information allowing a node to determine where the block belongs in the chain.

4.1 Hash Linking

A block can reference the hash of its predecessor. Changing the contents of an earlier block therefore changes the cryptographic relationship between that block and subsequent blocks.

4.2 Chain State

The blockchain represents the accepted transaction history and associated monetary state of the network.

5. Blocks

A block is a container for transactions together with metadata required by the consensus mechanism.

The exact binary serialization and field encoding are implementation-level details and must be defined by the NienCoin Core consensus specification before being treated as immutable protocol requirements.

5.1 Conceptual Block Fields

Field Purpose
Version Identifies the block format or consensus version.
Previous Block Hash Links the block to its predecessor.
Timestamp Provides block timing information.
Difficulty Target Represents the Proof-of-Work requirement.
Nonce Provides a value miners can vary during hashing.
Transactions Contains transactions included in the block.

5.2 Block Reward

A valid block may contain a reward transaction according to the monetary rules of the network.

The initial block reward defined for NienCoin is 10 NEC.

6. Transactions

Transactions represent transfers of NEC between participants.

A valid transaction must satisfy the rules enforced by NienCoin nodes.

6.1 Transaction Lifecycle

  1. A wallet creates a transaction.
  2. The transaction is authorized according to the wallet's cryptographic credentials.
  3. The transaction is transmitted to peers.
  4. Nodes verify the transaction.
  5. A miner may include the transaction in a block.
  6. Nodes validate the resulting block.
  7. The transaction becomes part of the accepted chain.

6.2 Transaction Inputs and Outputs

The exact transaction accounting model must follow the implementation's consensus specification.

Whether the final NienCoin implementation uses a UTXO model, account model, or another validated state representation must be determined by the Core protocol specification.

7. Proof-of-Work

Proof-of-Work requires a miner to perform computation before a candidate block can satisfy the network's difficulty requirement.

Cryptographic hashing allows nodes to verify a discovered result without repeating the entire search performed by the miner.

7.1 Mining Search

A miner modifies a variable such as a nonce or other permitted block data and repeatedly evaluates the block's Proof-of-Work function.

The process continues until the resulting value satisfies the current target.

Valid Block ⇔ ProofOfWork(Block Header) ≤ Target

7.2 Verification

A node receiving a candidate block calculates the required Proof-of-Work result and compares it with the target.

If the result does not satisfy the target, the block must be rejected.

7.3 Why Proof-of-Work Matters

Proof-of-Work makes block production consume computational resources. This gives the chain's history an associated amount of accumulated work.

An attacker attempting to rewrite historical blocks must reproduce the required work for the modified history and compete against continuing honest block production.

The security of this model depends on assumptions about the distribution of mining power and the implementation of the consensus rules.

8. Mining

Mining is the process by which participants attempt to create valid blocks.

8.1 Mining Process

  1. Select valid pending transactions.
  2. Construct a candidate block.
  3. Include the required previous-block reference.
  4. Construct the reward according to consensus rules.
  5. Search for a valid Proof-of-Work.
  6. Broadcast the discovered block.
  7. Wait for network validation.

8.2 Mining Reward

The initial NienCoin block reward is 10 NEC.

The reward is not a guaranteed financial return. Mining requires hardware, electricity, connectivity, and functioning software.

8.3 Mining and Supply

Mining is the intended mechanism through which newly issued NEC enters the circulating supply.

Once NEC has been issued and transferred, ownership can subsequently change through voluntary transactions between participants.

9. Difficulty Adjustment

A Proof-of-Work blockchain needs a mechanism for maintaining a predictable approximate block interval as total mining power changes.

NienCoin targets an average block interval of approximately five minutes.

The exact retarget algorithm, adjustment interval, limits, and timestamp rules are consensus parameters and must match the implementation.

Consensus requirement: The final Core implementation must define one deterministic difficulty calculation that every compatible node can reproduce.

10. Consensus

Consensus is the collection of rules used by nodes to determine whether blocks and transactions are valid.

10.1 Block Validity

A node should reject a block that violates any mandatory consensus rule.

Examples include an invalid Proof-of-Work, invalid predecessor reference, invalid transaction data, or an invalid reward.

10.2 Determinism

Consensus validation must be deterministic. Given the same blockchain data and the same consensus rules, compatible nodes should reach the same validity result.

10.3 Invalid Blocks

Nodes must not accept an invalid block merely because it was received from a trusted peer.

The block itself must satisfy the protocol.

11. Nodes

A node is software that participates in the NienCoin network and maintains or validates blockchain data.

11.1 Full Node Responsibilities

  • Receive network messages.
  • Validate transactions.
  • Validate blocks.
  • Maintain blockchain state.
  • Relay valid data.
  • Reject invalid data.
  • Maintain peer connections.

11.2 Independent Verification

Running an independent node allows a participant to verify the network without relying entirely on another participant's interpretation of the blockchain.

12. Peer-to-Peer Network

NienCoin is intended to use peer-to-peer communication so that blockchain data can propagate between participating nodes.

12.1 Transaction Propagation

When a node receives a valid transaction, it may relay that transaction to connected peers.

12.2 Block Propagation

When a miner discovers a valid block, the block can be broadcast to peers for validation and further propagation.

12.3 Peer Discovery

The final implementation may use seed nodes, manually configured peers, DNS discovery, or another mechanism.

The exact mechanism is a software and network specification detail rather than a monetary rule.

13. Wallets and Addresses

A wallet provides an interface for managing cryptographic credentials and creating transactions.

13.1 Ownership

Control over the cryptographic credentials associated with an address is the practical mechanism by which a participant authorizes transfers.

13.2 Address Generation

NienCoin addresses must be generated according to a deterministic protocol format defined by the implementation.

The final address prefix, encoding and checksum format should be documented once the Core protocol is frozen.

13.3 Wallet Security

Users are responsible for protecting wallet credentials and backups.

Loss of private credentials may result in loss of control over associated funds.

The maximum supply establishes an upper boundary for the number of whole NEC units that can exist under the intended monetary rules.

New NEC is intended to be issued through valid block rewards.

14.3 Supply Verification

Nodes should be able to calculate the permitted monetary issuance from the blockchain history and consensus rules.

15. Supply Distribution

NienCoin uses a mining-oriented distribution model.

The intended model does not depend on a hidden allocation of the entire supply to a predetermined owner.

Participants can obtain NEC by contributing valid Proof-of-Work mining or by receiving NEC from another participant.

15.1 Mining

Mining is the primary mechanism for the creation of new NEC according to the protocol.

15.2 Secondary Transfer

An individual who does not mine can obtain NEC through a voluntary transaction with an existing holder.

15.3 No Guaranteed Value

Possession of NEC does not guarantee a particular monetary value or exchange rate.

17. Genesis Block

The genesis block is the first block of the NienCoin blockchain.

It establishes the initial chain state from which subsequent blocks are linked.

17.1 Genesis Immutability

Once the network's genesis block is established as part of the protocol, compatible nodes must recognize the same genesis identity.

17.2 Genesis Configuration

The final implementation should publish the genesis block hash and all consensus-critical genesis parameters.

18. Security Model

NienCoin's security depends on cryptographic primitives, consensus validation, Proof-of-Work, node diversity, and correct implementation.

18.1 Cryptographic Integrity

Cryptographic hashes are used to detect changes to data and to link blockchain history.

18.2 Proof-of-Work Security

Rewriting history requires reproducing the associated Proof-of-Work and competing with continuing chain growth.

18.3 Majority Mining Power

A Proof-of-Work network is exposed to increased reorganization and censorship risk if an attacker controls a sufficiently large share of effective mining power.

18.4 Software Bugs

Cryptographic security does not protect against implementation errors. Consensus software must therefore be tested carefully.

19. Decentralization

Decentralization is not a single technical feature. It depends on the number and diversity of nodes, miners, developers, infrastructure providers and users.

19.1 Node Diversity

A healthy network should have multiple independent nodes rather than relying on one server.

19.2 Mining Diversity

Mining concentration can increase the influence of large operators over block production.

19.3 Open Participation

The project aims to make participation possible through publicly available software and protocol documentation.

20. Economic Model

NienCoin's monetary model combines limited supply with Proof-of-Work issuance.

The economic value of NEC is not determined by the protocol alone. Market demand, liquidity, adoption, utility and participant behavior can all affect value.

20.1 Mining Incentive

The block reward provides an incentive for miners to contribute computational resources to the network.

20.2 Network Security

Mining incentives are connected to network security because miners have an economic reason to produce valid blocks.

20.3 Market Value

The protocol does not guarantee that NEC will have a particular market price.

No investment guarantee: NienCoin should not be described as guaranteeing profit, appreciation, mining income or exchange liquidity.

21. Transaction Fees

Transaction fees can be used to compensate miners for including transactions in blocks, particularly as block subsidy changes over time.

The final NienCoin fee policy must be defined by consensus and transaction-selection rules.

21.1 Fee Validation

Nodes must verify that a transaction does not create unauthorized value when fees are calculated.

21.2 Miner Selection

Miners may prioritize transactions according to transaction fees and other policy rules, provided that consensus validity is preserved.

22. Transaction Validation

A transaction should only enter an accepted block if it satisfies all applicable consensus conditions.

22.1 Basic Validation Principles

  • Transaction structure must be valid.
  • Authorization must be valid.
  • Inputs or account state must permit the transfer.
  • The transaction must not create unauthorized value.
  • Required fees must be satisfied.

22.2 Block-Level Validation

Block validation combines transaction validation with block-level rules such as Proof-of-Work, block linkage, timestamps, reward limits, and difficulty requirements.

23. Forks and Chain Selection

Two valid blocks can occasionally be produced at approximately the same time.

Different nodes may temporarily observe different tips of the chain.

23.1 Temporary Forks

A temporary fork can resolve when additional valid Proof-of-Work causes one branch to become preferred according to the chain-selection rule.

23.2 Consensus Forks

A permanent consensus split can occur when different software versions enforce incompatible consensus rules.

23.3 Protocol Upgrades

Consensus changes should be documented carefully because incompatible changes can divide the network.

24. Chain Reorganizations

A chain reorganization occurs when a node changes its preferred chain because another valid branch has greater accumulated consensus weight according to the network's chain-selection rule.

Applications should not assume that an unconfirmed transaction or newly mined block is permanently irreversible immediately after first observation.

25. Confirmations

A transaction included in a block has one block-level confirmation. Additional blocks built on top of that block increase its depth in the chain.

More confirmations generally make a reorganization affecting that transaction more difficult, assuming the network's Proof-of-Work security assumptions hold.

26. Double Spending

Double spending refers to attempting to use the same spendable value more than once.

Consensus validation prevents conflicting transactions from both becoming valid representations of the same underlying spendable state.

26.1 Confirmation Risk

Transactions that have not yet received sufficient confirmation should not automatically be treated as irreversible.

27. Security Threats

NienCoin may face technical attacks common to public Proof-of-Work blockchain systems.

27.1 Majority Hashrate Attack

An entity controlling a large fraction of network mining power may have increased ability to reorganize recent blocks or influence transaction ordering.

27.2 Sybil Attack

An attacker may create many network identities. Peer-to-peer network design should therefore avoid treating the number of IP addresses as equivalent to economic or computational consensus power.

27.3 Eclipse Attack

A node may be isolated from honest peers if an attacker controls enough of its network connections.

27.4 Denial of Service

Nodes may be targeted with excessive or malformed network traffic.

27.5 Consensus Bug

An implementation bug affecting validation can cause incompatible nodes to disagree about the blockchain.

28. Privacy

A public blockchain generally exposes transaction information to network participants.

NienCoin should not be described as automatically anonymous merely because users interact through cryptographic addresses.

28.1 Public Ledger

Blockchain data may allow observers to analyze transaction relationships and activity.

28.2 User Responsibility

Users should understand that publishing or linking an address to a real-world identity can reduce practical privacy.

29. NienCoin Core Software

NienCoin Core is intended to provide the software necessary for interacting with the blockchain.

29.1 Core Responsibilities

  • Blockchain validation
  • Transaction processing
  • Block processing
  • Peer communication
  • Mining integration
  • Wallet functionality where implemented

29.2 Compatibility

Nodes running compatible consensus software should independently arrive at the same valid chain state when supplied with the same valid blockchain history.

30. Open Development

NienCoin is intended to be developed transparently, with source code and technical documentation available for inspection.

Open development allows independent contributors to inspect implementation decisions, report bugs and propose improvements.

30.1 Reproducibility

Build instructions should allow users and developers to reproduce official software releases from published source code whenever practical.

30.2 Testing

Consensus-critical software should receive extensive testing before production deployment.

31. Governance

NienCoin does not rely on a single centralized administrator to determine whether ordinary blocks are valid.

Network participants enforce the consensus rules implemented by their software.

31.1 Protocol Changes

Proposed consensus changes should be documented, reviewed and tested before adoption.

31.2 Community Participation

Developers, node operators, miners and users can contribute to discussions surrounding future development.

33. Limitations

NienCoin is a software project and may contain bugs, incomplete components, performance limitations and security weaknesses.

A blockchain protocol cannot guarantee adoption, liquidity, exchange availability or market value.

Network security depends on actual participation. A small network with limited mining power can have weaker resistance to certain attacks than a large, highly distributed network.

34. Risks

34.1 Technical Risk

Software bugs can affect wallets, nodes, miners or consensus validation.

34.2 Network Risk

A small number of active peers or miners can make the network more vulnerable to disruption.

34.3 Economic Risk

The value of NEC may be highly uncertain and can change independently of the technical quality of the software.

34.4 Development Risk

Future features may be delayed, redesigned or abandoned.

34.5 Regulatory Risk

Digital-currency projects may be subject to laws and regulations that vary between jurisdictions.

35. Future Development

Future development may focus on improving the reliability, usability, security and transparency of the NienCoin ecosystem.

35.1 Protocol Improvements

Consensus improvements may be considered when technically justified and compatible with the project's design principles.

35.2 Wallet Improvements

Wallet software may become easier to use while maintaining strong control over private credentials.

35.3 Developer Infrastructure

Documentation, APIs, testing tools and development environments may be expanded.

35.4 Network Infrastructure

Public nodes, monitoring systems and explorer infrastructure may improve network visibility.

36. Conclusion

NienCoin is an independent Proof-of-Work Layer-1 blockchain designed around a limited monetary supply, mining-based issuance and peer-to-peer participation.

The network defines a maximum supply of 20,000,000 NEC and an initial block reward of 10 NEC, with a target block interval of five minutes.

The currency is divisible into 100,000,000 Huu Khang per NEC.

1 NEC = 100,000,000 Huu Khang

The fundamental objective of the project is to build a blockchain whose operation can be independently verified by nodes and whose monetary issuance follows explicit protocol rules.

The technical implementation remains the ultimate source of truth for consensus behavior. This whitepaper describes the intended design and should evolve alongside the finalized NienCoin protocol specification.
